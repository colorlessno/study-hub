# devops10 運用証拠によるリリース判定

ビルド、テスト、API、health、readiness、ログ、ロールバック手順の確認結果を一つの記録へまとめ、リリース可否を判断するテーマです。

## このテーマでできるようになること

- 自動確認と運用確認の証拠を分けて記録できる
- 証拠が未確認、成功、失敗のどれかを明示できる
- 未解決のリスクとロールバック手順を判断材料に含められる
- リリース可、条件付き可、リリース不可を根拠とともに記録できる

## 最初に取り組むこと

1. 「教材を表示」でリリース判定画面を開く。
2. 「固定シナリオを読み込む」を押し、各手順に入る証拠を確認する。
3. ビルドやテストの成功だけで判断せず、health、readiness、ログ、ロールバック手順も確認する。
4. 未解決のリスクを残した状態で、条件付き可またはリリース不可を選ぶ。
5. 記録をブラウザ内へ保存し、再読み込み後に復元されることを確認する。
6. Markdownをダウンロードし、証拠と判断が対応していることを確認する。
7. 「CI workflow」で、証拠資料、記入例、判定記録変換処理を順番に検査するstepを確認する。

入力内容はブラウザ内だけに保存されます。実在する秘密情報、個人情報、顧客情報は入力しないでください。

## arch02との違い

`StudyArchitecture arch02` は、設計上の主張と根拠を対応付け、設計の妥当性をレビューする独立テーマです。

`StudyDevOps devops10` も独立したテーマで、リリース候補に対して実行済みの確認結果を集め、運用開始してよいかを判断します。arch02の別名入口ではありません。設計書全体のレビューではなく、リリース直前の確認と判断記録が対象です。

## 画面で扱う証拠

| 分類 | 確認する内容 |
|---|---|
| 自動確認 | build、test、CI、API応答、DB変更 |
| 運用確認 | health、readiness、ログ、監視、request ID |
| 復旧準備 | ロールバック手順、実施確認、担当者 |
| 判断 | 未解決リスク、判定、条件、根拠 |

## 自分の言葉で説明する

- testが成功していてもreadinessが未確認なら、なぜリリース可と断定できないか。
- healthとreadinessは、それぞれ何を確認するために使うか。
- 条件付き可にした場合、誰がいつまでに何を確認する必要があるか。
- ロールバック手順が未確認のままリリースする場合、どのリスクが残るか。
