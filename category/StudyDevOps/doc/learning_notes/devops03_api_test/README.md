# devops03 Web APIの自動テスト

実際にWeb APIを起動し、正常な処理と入力エラーを外部から自動確認するテーマです。

## このテーマでできるようになること

- Docker ComposeでWeb APIとテストを実行できる
- HTTP状態コードとエラーコードを対応付けられる
- 入力エラーの後もAPIが動作していることを確認できる
- 失敗時のコンテナログからAPIとテストのどちらを調べるか判断できる

## 最初に取り組むこと

1. 「Web APIのソース」で稼働確認と登録処理を確認する。
2. 「Web APIのテスト」で送信内容と期待結果を確認する。
3. 「Docker Compose構成」でAPIとテストの接続先を確認する。
4. APIを起動し、「Web APIの自動テストを実行」を選ぶ。
5. 「実際のGitHub Actions定義」で、自動テスト、失敗ログ表示、後片付けの順序を確認する。

## 確認する内容

自動テストは、稼働確認、正常な登録、必須項目の不足、壊れたJSON、大きすぎる入力、存在しないURLを確認します。

必須項目の不足と壊れたJSONはどちらも400ですが、応答のエラーコードが異なります。大きすぎる入力は413、存在しないURLは404になります。入力エラーの後に再度稼働確認を行い、APIが停止していないことも確認します。

GitHub Actionsでは自動テストが失敗した場合だけ`docker compose logs`を実行し、その後は成功・失敗にかかわらずコンテナと保存領域を削除します。APIの起動失敗はapiサービス、期待値の不一致はtestサービスのログから調べます。

## 自分の言葉で説明する

- HTTP状態コードと応答内のエラーコードを分ける理由
- 入力エラーの後に稼働確認を行う理由
- Docker Compose内でサービス名を接続先に使う理由
- 自動テスト失敗時にapiとtestのどちらのログから確認するか
