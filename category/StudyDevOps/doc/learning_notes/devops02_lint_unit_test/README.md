# devops02 静的検査と単体テスト

ソースの書式を調べる静的検査と、処理結果を調べる単体テストの役割を分けて確認するテーマです。

## このテーマでできるようになること

- 静的検査と単体テストを個別に実行できる
- それぞれが確認する内容の違いを説明できる
- 両方を順番に実行する確認処理を使える
- 意図的な失敗例から、静的品質の失敗と振る舞いの失敗を分類できる

## 最初に取り組むこと

1. 「計算処理のソース」で公開されている処理を確認する。
2. 「単体テスト」で入力と期待結果を確認する。
3. 「静的検査の処理」で検査対象の書式を確認する。
4. 静的検査、単体テスト、両方の確認を順に実行する。
5. 「失敗ログの再現手順」で、二種類の失敗を安全に再現して元へ戻す手順を確認する。
6. 「実際のGitHub Actions定義」で、lintの後に単体テストが実行される順序を確認する。

## 確認する内容

静的検査は、ソースの書式や決められた規則への違反を調べます。単体テストは、関数へ入力を渡したときに期待した結果になるかを調べます。

どちらか一方だけでは確認できない問題があるため、両方を実行します。まとめて実行する処理は、静的検査が成功した後に単体テストへ進みます。

Dockerfileでも`npm run check`を実行するため、StudyHub、ローカル、Docker、GitHub Actionsで同じlintと単体テストを順番に確認できます。

## 自分の言葉で説明する

- 静的検査だけでは計算結果の誤りを見つけられない理由
- 単体テストだけでは書式の問題を見落とす理由
- 二つの確認を分けて結果を表示する利点
- 失敗したコマンド名とログから、修正すべきファイルを判断する方法
