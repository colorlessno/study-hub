# security13 レート制限

同じ利用者から短時間に要求が集中したとき、上限を超えた要求を429で拒否する仕組みを確認します。

## このテーマで確認すること

- 時間窓内の3回までは許可され、4回目が拒否される
- 時間窓の境界を過ぎると、回数がリセットされる
- 利用者を表すキーが異なれば、回数も別に管理される
- 応答の残り回数と`Retry-After`を確認できる
- メモリ上の回数は、複数サーバー間では共有されない

## 最初に取り組むこと

1. StudyHubの「起動」を押す。
2. 「3回許可・4回目拒否」を実行し、`statuses`が`200, 200, 200, 429`になることを確認する。
3. 「時間窓のリセット」を実行し、10秒の境界で再び200になることを確認する。
4. 「利用者ごとの回数分離」を実行し、2人の残り回数が別に管理されることを確認する。
5. 「回数と時間窓の判定処理」を表示し、画面の結果と条件分岐を照合する。

## 画面で確認できる結果

| 操作 | 確認する結果 |
|---|---|
| 3回許可・4回目拒否 | 同じキーへの4回目が429になる |
| 時間窓のリセット | 境界時刻から回数が1回目へ戻る |
| 利用者ごとの回数分離 | 別のキーは独立した残り回数を持つ |
| 1回の要求と残り回数 | 応答ヘッダーに上限と残り回数が表示される |

## 実装の対応

- `app/server.js`は要求から利用者のキーを決め、200または429を返す。
- `app/rate_limiter.js`はキーごとの回数と時間窓を管理する。
- `/health`は起動確認用で、レート制限の対象外にしている。

## 教材の範囲

この教材は1台のローカルサーバーとメモリ上の回数だけを扱います。実運用では、信頼できる利用者識別、複数サーバーで共有する保存先、期限切れキーの削除、経路ごとの上限を別途設計します。
