# security06 SQL Injection対策

同じ検索条件を文字列連結とパラメータ化したSQLへ渡し、入力値をSQL構文から分離する対策を確認する教材です。実DBは使わず、生成されたSQL本文とパラメータ配列を比較します。

## このテーマでできるようになること

- 入力値を直接連結したSQLの問題を確認できる
- SQL本文のplaceholderとパラメータ配列の対応を確認できる
- 検索条件が省略された場合もplaceholderの順序を保つ必要性を説明できる
- 入力検証とパラメータ化が別の役割を持つことを説明できる

## 最初に取り組むこと

1. StudyHubの「攻撃文字列の危険・安全なSQLを比較」を選ぶ。
2. `unsafeSql`と`safeQuery.sql`を比較し、入力値がどこに入るか確認する。
3. 「商品名だけの検索条件を確認」と「状態だけの検索条件を確認」を順に実行する。
4. 条件の有無によって`$1`と`$2`の割り当てが変わることを確認する。
5. 「安全・危険なSQL構築の実装」と「パラメータ化の説明」を開き、表示結果と処理を照合する。

## 画面で確認する内容

- 危険なSQLでは、攻撃文字列がSQL本文へ直接入る
- 安全なSQLでは、SQL本文に`$1`と`$2`だけが入り、値は`params`へ分離される
- 商品名だけの場合は商品名が`$1`になる
- 状態だけの場合は状態が`$1`になり、欠けた条件の番号を残さない
- `%`を含む部分一致用の値もSQL本文ではなく`params`へ入る

## 実装との対応

`app/query_builder.js`の`unsafeSearch`は文字列連結を行い、`safeSearch`は条件を追加するたびに値を`params`へ追加してplaceholder番号を決めます。列名や並び順などSQL構造に関わる値は、この方法ではなく許可済み候補から選びます。

## 学習用実装の範囲

- 実DB、DB driver、ORMは使用しない
- SQLを実行せず、構築されたSQLと値の分離だけを確認する
- トランザクション、DB権限、監査ログは扱わない
