# security04 ABAC 要件定義

## 1. 目的

roleだけでなく、ユーザー部署、対象データの部署、注文状態等の属性を組み合わせた認可を学ぶ。

## 2. 学習対象

- ABAC
- user attribute / resource attribute
- policy function
- 属性の信頼境界
- RBACとの使い分け

## 3. 作成する成果物

- ABACサンプル
- ポリシー例
- 部署一致・不一致の拒否例
- 注文状態による更新拒否例

## 4. 機能要件

| ID | 要件 |
|---|---|
| FR-01 | ユーザーにroleとdepartmentを持たせられる |
| FR-02 | 対象データにdepartmentとstatusを持たせられる |
| FR-03 | 管理者または部署一致ユーザーだけが注文を参照できる |
| FR-04 | 参照可能かつ`draft`の注文だけを更新できる |
| FR-05 | 存在しない注文は404、認証なしは401、属性条件不一致は403にできる |

## 5. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | 認可に使う属性をrequest bodyから信用しない |
| NFR-02 | ポリシー条件を共通関数として確認できる |
| NFR-03 | 拒否時に内部の属性値やポリシー詳細を返さない |

## 6. 対象外

- 本物の認証基盤とユーザーDB
- owner_id / tenant_idによるrow単位のscope
- policy engineやrow level securityの本格実装
- 複雑な組織階層と属性同期

## 7. 受入条件

- 部署一致ユーザーと不一致ユーザーの応答を比較できる
- `draft`と`confirmed`で更新可否が変わることを確認できる
- RBACとABACの違いを説明できる
- 属性をサーバー側の信頼できる情報から取得する理由を説明できる

## 8. 学習観点

- roleだけで表しにくい条件を属性で補う
- user、resource、environmentのどの属性を信頼するかを決める
- ポリシーを増やすほど、確認ケースと監査可能性が重要になる
