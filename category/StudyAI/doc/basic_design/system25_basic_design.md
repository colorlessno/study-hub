# System 25 基本設計

## 対象

同じ指示を実モデルへ送り、出力上限とTemperatureの組み合わせを複数回比較する。StudyHubの画面、StudyAIのAPI、共通LLMクライアント、LM Studio、履歴ファイルを使用する。

## 利用者から見た流れ

1. StudyHubでsystem25を開く。
2. 指示、モデル、出力上限、Temperature、試行回数を確認する。
3. 実モデルを使用する場合は`mode`を`model`にして実行する。
4. 試行ごとの回答と終了理由を確認する。
5. 条件別集計から途中切れと回答差を比較する。
6. 候補設定、判断理由、保存状態を確認する。

## システムのつながり

```text
StudyHubのsystem25画面
  ↓ POST /api/system25/execute
StudyAI API
  ↓ LearningSystemService
出力上限 × Temperature × 試行回数の実行制御
  ↓ LLMClient
LM StudioのOpenAI互換API
  ↓ 回答・finish_reason・usage・model
条件別集計と候補設定の選定
  ↓
画面表示 + data/ai_learning/system25_runs.json
```

## 役割分担

| 対象 | 役割 |
|---|---|
| system25画面 | 入力JSONの編集、実行、試行結果、集計、候補設定、学習メモの表示 |
| APIルーター | system25の入力をサービスへ渡し、実行結果と履歴を返す |
| LearningSystemService | 入力検証、全条件の試行、途中切れ判定、集計、候補選定、履歴保存 |
| LLMClient | モデル、Temperature、max_tokensをOpenAI互換APIへ送信し、回答メタデータを返す |
| LM Studio | 指定条件で文章を生成する |
| 履歴ファイル | 直近20件の入力、結果、学習メモを保持する |

出力上限、Temperature、試行番号の順に一件ずつ処理し、直前のLLM応答を取得して記録した後に次の試行へ進む。同時送信や並列処理は行わない。

## 入力設計

| 項目 | 内容 |
|---|---|
| prompt | 全試行で固定する指示。1～8000文字 |
| model | LM Studioで使用するモデル名 |
| max_tokens_values | 1～4096の重複しない整数。1～5件 |
| temperatures | 0～2の重複しない数値。1～5件 |
| trial_count | 各条件の試行回数。1～5回 |
| mode | `model`または`mock` |
| learning_note | 観察結果、採用判断、残る注意点 |

## 実行結果設計

試行結果には、出力上限、Temperature、試行番号、回答、回答文字数、入力・出力トークン数、`finish_reason`、途中切れ、応答時間、応答モデルを持たせる。

条件別集計には、試行数、途中切れ回数と率、異なる回答数、平均回答文字数、平均出力トークン数、平均応答時間を持たせる。

候補設定は、途中切れがない条件を優先し、その中で平均出力トークン数と平均応答時間が小さい条件を選ぶ。これは教材用の機械的な候補であり、学習者が最終判断を学習メモへ記録する。

## 通信失敗時の扱い

実モデルの通信失敗、タイムアウト、応答形式不正はエラーとして返す。自動的にモックへ切り替えない。モックは画面と比較手順を確認するための明示的な選択肢として分離する。

## 保存設計

履歴は`data/ai_learning/system25_runs.json`へUTF-8で保存する。直近20件を保持し、一時ファイルを書いた後で保存先を置き換える。起動時にファイル形式を検証し、不正な履歴を黙って無視しない。

## 確認方法

- 短い出力上限で`finish_reason=length`が途中切れとして集計されることを確認する。
- 同一条件を複数回実行し、Temperature別の異なる回答数を確認する。
- モデル、出力上限、TemperatureがLLMクライアントへ渡ることを確認する。
- 実モデルとモックが明示的に区別されることを確認する。
- 保存後にサービスを作り直し、履歴が復元されることを確認する。
