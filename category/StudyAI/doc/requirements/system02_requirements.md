## 契約書・文書 リスク審査システム

---

## システム概要

日本法準拠の契約書や各種文書をアップロードすると、LLMがリスク箇所・不利な条件・抜け漏れを検出し、指摘事項と修正案を返すシステム。法務・購買部門の一次審査工数を削減し、見落としリスクを低減する。

---

## 現状の課題

- 契約書の読み込みに時間がかかり、法務担当者の工数が大きい
- 担当者のスキルによってリスク検出の品質にばらつきがある
- 不利な条件・抜け漏れの見落としが契約後のトラブルにつながる
- 専門用語が多く、法務経験の浅い担当者では対応が難しい

---

## 対象ユーザー

- 法務担当者
- 購買・調達担当者
- 経営者・管理職（契約確認が必要な場面）

## 機能要件

### 1. ファイルアップロード機能
- 対応形式：PDF・Word（.docx）・テキスト（.txt）
- ファイルサイズ上限：1ファイルあたり20MB
- 比較審査では2文書を受け付け、文書Aの審査、文書Bの審査、差分審査を一つずつ順番に実行する
- 対象文書は日本法準拠の契約書に限定する
- 受入対象は原則として1文書あたり50ページ以内、比較審査は2文書合計100ページ以内

### 2. 文書種別判定機能
LLMが文書の種別を自動判定する。

| 文書種別 | 説明 |
|---------|------|
| 業務委託契約書 | 委託・受託の範囲・報酬・成果物 |
| 売買契約書 | 売買条件・価格・納期・保証 |
| NDA（秘密保持契約） | 秘密情報の範囲・期間・義務 |
| 賃貸借契約書 | 賃料・期間・原状回復 |
| 雇用契約書 | 労働条件・給与・解雇条件 |
| その他 | 上記に該当しない文書 |

### 3. リスク審査機能
LLMが以下の観点で文書を審査し、指摘事項を生成する。

**① 不利な条件・リスク箇所**
- 一方的に不利な責任・賠償条項
- 過度に広い秘密保持・競業避止義務
- 不明確な成果物・納品基準の定義
- 解除条件・違約金の非対称性
- 自動更新・解約通知期限の見落とし

**② 抜け漏れ・未定義項目**
- 準拠法・管轄裁判所の未記載
- 知的財産権の帰属が未定義
- 支払条件・遅延損害金の未記載
- 個人情報の取り扱い条項の欠如
- 変更・修正手続きの未規定

**③ 法的観点の確認事項**
- 印紙税の要否
- 電子契約の有効性
- 強行法規違反の可能性
- 消費者契約法・労働法等の適用可能性

### 4. 修正提案機能
各指摘事項に対して以下をセットで返す。

| 項目 | 説明 |
|------|------|
| 指摘箇所 | 該当する条項番号・条文テキスト |
| リスク種別 | 不利条件 / 抜け漏れ / 法的確認 |
| 深刻度 | 致命的・高・中・低 |
| 指摘内容 | 何が問題か |
| リスクの説明 | なぜリスクなのか |
| 修正案 | 修正後の条文テキスト |

### 5. サマリー生成機能
- 指摘件数（リスク種別・深刻度別）
- 総合リスク評価（高リスク・中リスク・低リスク）
- 優先的に対応すべき指摘のトップ3
- 締結推奨度（AIによる一次審査の参考情報として、低リスクはそのまま締結可、中リスクは要修正後締結、高リスクは締結不推奨を返す）

### 6. 比較審査機能（オプション）
- 2つの文書（自社ひな形 vs 相手方提示版）を比較し、差分と追加リスクを抽出する

### 7. 結果保存・取得機能
- 審査結果をPostgreSQLに保存する
- 過去の審査結果を取得・比較できる
- 同一文書の再審査時に前回との差分を表示できる
- 原文ファイル、本文、原文条文・抜粋はDBに保存しない。保存対象はファイルハッシュ、審査条件、サマリー、指摘・修正案とする
- 保存済み結果の詳細と2件比較を画面から実行できる

---

## 非機能要件

| 項目 | 要件 |
|------|------|
| 応答時間 | 50ページ以内の1文書あたり90秒以内 |
| セキュリティ | アップロードファイルは処理後に削除。文書内容はDBに保存しない（ハッシュのみ） |
| 対応言語 | 日本語・英語（日本法準拠文書に限る） |
| 免責事項 | 本システムの審査結果は参考情報であり、法的判断は弁護士等の専門家に委ねること |

---

## システム構成

```
クライアント（curl / 画面）
        ↓
    FastAPI（APIサーバー）
        ↓
    ファイル受付・テキスト抽出
    （PDF→テキスト / Word→テキスト）
        ↓
    文書種別判定（LLM）
        ↓
    文書分割処理
    （長文の場合は条項単位でチャンキング）
        ↓
    LLM（3観点審査・修正案生成）
        ↓
    出力バリデーション（Pydantic）
    ※ JSON壊れ時は再試行（最大3回）
        ↓
    PostgreSQL（審査結果保存）
        ↓
    MLflow（モデル名・処理時間・件数・トークン数・再試行回数を記録）
        ↓
    JSONレスポンス返却
```

## API仕様

### POST /review
文書をアップロードして審査を実行する。

**リクエスト**
```
Content-Type: multipart/form-data
file: アップロードファイル（PDF / Word / テキスト）
perspective: 審査視点（契約類型ごとの当事者ロール。例："受託者" / "委託者" / "買主" / "売主" / "賃借人" / "賃貸人" / "労働者" / "使用者" / "中立"）
```

### POST /compare
2文書を比較審査する。

**リクエスト**
```
Content-Type: multipart/form-data
file_a: 自社ひな形
file_b: 相手方提示版
perspective: 審査視点
```

### GET /reviews
過去の審査結果一覧を取得する。

**クエリパラメータ**
```
document_type: 文書種別
overall_risk:  総合リスク評価
from_date:     開始日
to_date:       終了日
```

### GET /reviews/{review_id}
指定した審査結果の詳細を取得する。

### GET /reviews/compare
2回分の審査結果を比較し、追加・解消されたリスクと推奨度の変化を返す。

## データモデル

### contract_reviewsテーブル
```sql
CREATE TABLE system02_contract_reviews (
    id              SERIAL PRIMARY KEY,
    file_name       VARCHAR(255),
    file_hash       VARCHAR(64),
    document_type   VARCHAR(50),
    perspective     VARCHAR(20),
    overall_risk    VARCHAR(20),   -- 高リスク・中リスク・低リスク
    recommendation  VARCHAR(30),   -- そのまま締結可・要修正後締結・締結不推奨
    summary         JSONB,
    total_issues    INTEGER,
    created_at      TIMESTAMP DEFAULT NOW()
);
```

### contract_issuesテーブル
```sql
CREATE TABLE system02_contract_issues (
    id               SERIAL PRIMARY KEY,
    review_id        INTEGER REFERENCES system02_contract_reviews(id),
    issue_type       VARCHAR(20),   -- unfavorable・missing・legal_check
    severity         VARCHAR(20),   -- critical・high・medium・low
    article          VARCHAR(50),
    description      TEXT,
    risk_explanation TEXT,
    suggested_text   TEXT
);
```

> `original_text` は実行直後のAPIレスポンスでは返してよいが、DBと保存済み結果の詳細・比較応答には保存・再掲しない。

## プロンプト仕様

### システムプロンプト
```
あなたは日本法準拠の契約書審査の専門家AIです。
アップロードされた文書を指定の視点（契約類型ごとの当事者ロールまたは中立）から審査し、
リスク箇所・抜け漏れ・法的確認事項を指定のJSONフォーマットで出力してください。

ルール：
1. 必ず指定のJSONフォーマットで返すこと
2. 指摘には必ず修正案をセットで示すこと
3. 深刻度はcritical / high / medium / lowの4段階で判定すること
4. 法的判断が必要な箇所はlegal_checkとして分類し、専門家確認を促すこと
5. 推測・憶測で指摘せず、文書に明示された内容のみを根拠にすること
6. 重要度の高い指摘から最大3件へ絞り、説明と修正案は簡潔にすること
7. 本システムの出力は参考情報であり、最終判断は専門家に委ねる旨をsummaryに含めること
```

### Chain-of-Thought設計
- まず文書種別を判定させる
- 次に条項を一覧化させる
- 各条項について観点別にリスクを評価させる
- 最後にサマリーを生成させる

---

## ガードレール設計

- JSON形式が壊れていた場合：最大3回まで再試行
- JSON生成では思考過程を出力せず、指定形式の審査結果だけを返す
- 文書が長文の場合：条項単位でチャンキングして処理し、最後に統合
- 比較審査の場合：文書A、文書B、差分の順に一つずつLLMへ送信し、同時送信しない
- 対応外のファイル形式の場合：即時エラーレスポンス
- 処理時間が90秒を超えた場合：タイムアウトエラーとしてログに記録
- 法的断言を避ける：「〜のリスクがあります」「専門家に確認してください」の文言を必須にする
- MLflowと監査ログには原文・プロンプト本文を残さない

- 判例・法令データベースとの連携
