# system48 要件定義

## このテーマでできるようになること

- 1つのAIに全てを任せる構成と、役割分担したAI組織構成の違いを説明できる
- タスクボード、共有記憶、判断ログ、レビュー結果の役割を説明できる
- ローカルLLMへの処理を必ず順番に実行する理由を説明できる
- 人間確認が必要な操作と、AIだけで進めてよい操作を分けて説明できる
- 模擬実行でも、計画、レビュー、QA、最終報告の成果物が残る

## ローカルLLMによるAI組織運用

## 1. 目的

ローカルLLMを使い、複数のAIエージェントを役割分担させて、タスクボード、共有文書、レビュー、承認境界を通じて組織のように運用する設計を学ぶ。

この教材では、1つのAIに全ての文脈と判断を渡すのではなく、役割ごとに文脈を分け、書き物で引き継ぎ、複数の観点で品質を確認する構成を扱う。

## 2. 学習対象

- ローカルLLMを使った複数エージェント運用
- 役割分担による文脈分離
- タスクボードと保存済み文書を介した順次連携
- 共有記憶、判断ログ、引き継ぎ文書
- レビュー、QA、記録を含む品質保証
- 人間確認を挟む承認境界
- AIに許可する操作と禁止する操作の明文化
- ローカルLLM未接続時の模擬実行と固定入力データ実行

## 3. 前提

- `system45` のエージェント技能パッケージ化で扱う、役割や手順を再利用可能な単位として切り出す考え方を前提にする。
- `system46` のAI実行基盤設計で扱う、入力、出力、検証、ログ、承認境界を前提にする。
- 既存 StudyAI の LM Studio 方針に合わせ、ローカルLLMは OpenAI互換APIとして扱う。
- ローカルLLMを複数同時起動する前提にはしない。MVPでは同一モデルを役割ごとに順番に呼び出す。
- 外部AI APIに依存しない。未接続時も学習できるよう模擬実行を用意する。

## 4. 機能要件

| ID | 要件 |
|---|---|
| FR-01 | AI組織の役割定義として、PM、計画、設計、実装計画、レビュー、QA、記録、安全確認の8ロールを既定で定義する。役割数は設定ファイルで変更可能とする。 |
| FR-02 | 各ロールには、そのロールが読むべき入力文書、書くべき成果物、判断してよい範囲を定義する。 |
| FR-03 | エージェント同士の直接会話ではなく、タスクボード、判断ログ、作業メモ、レビュー結果を介して連携する。 |
| FR-04 | 1つの依頼を、計画、実行案作成、レビュー、QA観点抽出、最終報告の流れで処理する。 |
| FR-05 | ローカルLLM接続時は LM Studio の OpenAI互換APIを利用し、未接続時は決定的な模擬応答で同じ流れを再現する。 |
| FR-06 | ファイル変更、ファイル削除、コマンド実行、外部送信、依存追加、長時間実行は人間承認が必要な操作として扱う。秘密情報の利用とOS設定変更は承認の有無にかかわらず禁止する。 |
| FR-07 | 各実行で、入力、担当ロール、出力、レビュー結果、保留理由、承認待ち項目をログに残す。 |
| FR-08 | 無限ループを防ぐため、最大ラウンド数、再試行回数、停止条件を定義する。 |
| FR-09 | AIの出力品質だけで合否を判断せず、成果物の有無、必須項目、禁止操作違反、レビュー指摘の反映状況を機械的に確認する。 |

## 5. 非機能要件

- ローカルPCで学習できる構成にし、外部AI API課金を前提にしない。
- LM Studioが起動していない場合でも、模擬実行で手順と成果物の関係を確認できる。
- タスク、ログ、レビュー結果は後から読み返せるテキストまたはJSONで保存する。
- エージェントに全情報を渡さず、ロールごとに必要な文脈だけを渡す。
- 承認が必要な操作は承認前に実行せず、教材上は「承認待ち」として記録する。
- 作成するテキストファイルは UTF-8 BOMなしを原則とする。

## 6. 対象外

- 本番業務を24時間365日自律実行するAI組織の構築
- ファイル削除、外部送信、Git操作をAIが承認前に実行する仕組み
- OS設定変更をAIが実行する仕組み
- 複数GPUや複数ローカルLLMを同時に動かす推論基盤
- 実顧客情報、秘密情報、個人情報を使った運用
- 外部SaaSのタスクボード連携

## 8. 受入条件

- 1つのAIに全てを任せる構成と、役割分担したAI組織構成の違いを説明できる。
- タスクボード、共有記憶、判断ログ、レビュー結果の役割を説明できる。
- ローカルLLMへの処理を必ず順番に実行する理由を説明できる。
- 人間確認が必要な操作と、AIだけで進めてよい操作を分けて説明できる。
- 模擬実行でも、計画、レビュー、QA、最終報告の成果物が残る。
- 既定8ロールを設定ファイルで増減でき、設定した役割数と成果物数が一致する。
- ファイル削除が禁止扱いではなく承認待ちとして記録され、承認前に実行済みにならない。

## 9. 元データから反映した観点

- AIエージェントは人間の組織と同じように、役割、責任、引き継ぎ、レビューを設計しないと品質が安定しない。
- 1つのAIに全ての文脈を渡すと、無関係な情報が混ざり、出力がぶれやすい。
- 品質は個人の頑張りではなく、複数の観点とレビューの仕組みで担保する。
- エージェント間の連携は会話ではなく、タスクボードや文書に残す。
- AIには暗黙の了解が通じないため、やってよいこと、禁止すること、迷った時の扱いを明文化する。
- AI組織は静かに壊れることがあるため、定期的なログ確認と設定確認を設計に含める。

## 10. 優先度

StudyAI の追加候補としては、`system45` と `system46` の後に扱う優先度とする。

理由は、AI組織運用が技能パッケージ化、AI実行基盤、承認境界、ログ、模擬実行の上に成り立つためである。
