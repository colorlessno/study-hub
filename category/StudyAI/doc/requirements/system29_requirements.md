# System 29 要件定義
## chunk metadata設計

## 1. 目的
RAG の根拠追跡、権限制御、評価に使える metadata を設計する。

## 2. 学習対象
- AIシステムの要件定義、基本設計、詳細設計、製造に進むための最小単位のテーマとして扱う。
- 商品・顧客・注文管理へ統合する最終ポートフォリオは対象外とし、この番号では土台となる観察、比較、評価、データ品質だけを扱う。
- 既存 `system01` から `system16` の成果物は変更しない。

## 3. 対象ユーザー
- AIアプリケーションの設計・実装を学習する開発者
- RAG、LLM評価、ローカルAI実行環境の判断材料を整理したい学習者

## 4. 入力
- 文書
- 検索語
- 出典、ページ番号、章見出し、公開範囲、更新日時
- metadataフィルタ
- 観察結果、設計判断、残る注意点

## 5. 出力
- 文書断片とmetadata JSON
- metadataフィルタの判定と対象外理由
- 検索結果と根拠表示
- 保存状態と実行履歴

## 6. 機能要件
- chunk に source、page、section、permission、updated_at を付与できる。
- 検索結果に根拠を表示できる。
- metadata フィルタを確認できる。
- フィルタ条件に合わない文書断片を検索結果から除外できる。
- 観察結果、設計判断、残る注意点を実行結果と一緒に保存できる。

## 7. 非機能要件
- ローカルで再現できる小さなサンプルとして構成する。
- metadata付与、検索前フィルタ、検索語照合、根拠表示はStudyAIバックエンドで実行し、外部AI APIを使用しない。
- Docker に入れられる実装は `Dockerfile` または `docker-compose.yml` を用意する。
- 作成・更新するテキストファイルは UTF-8 BOMなしを原則とする。
- 評価や比較の結果は、後続の基本設計・詳細設計で参照できる形で保存する。

## 8. 受入条件
- metadata がない RAG の追跡困難さを説明できる。
- 監査や権限制御に必要な項目を整理できる。
- 一致するフィルタと一致しないフィルタで検索結果が変わることを確認できる。
- 検索結果から出典、ページ、章見出しへたどれる。
- 保存した実行結果を再起動後も参照できる。

## 9. 後続工程への引き継ぎ
- 基本設計では、入力、処理、出力、保存形式、画面またはCLIの境界を定義する。
- 詳細設計では、データ構造、比較指標、エラーケース、Docker 実行方法を定義する。
- 製造では、README、実行手順、サンプルデータ、確認コマンドを含める。

## 10. 対象外
- 本番クラウドへのデプロイ
- 課金が発生する外部APIを前提にした必須実装
- 商品・顧客・注文管理の統合ポートフォリオへの組み込み
