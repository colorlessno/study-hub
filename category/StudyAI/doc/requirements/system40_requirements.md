# System 40 要件定義

## このテーマでできるようになること

- LLMではなく予測と業務ルールの組み合わせとして説明できる
- 予測誤差と欠品リスクを分けて表示できる
- 自動発注ではなく承認フローを挟める

## 需要予測・在庫最適化AI

## 1. 目的
需要予測、在庫数、発注点、欠品リスク、補充提案、人間承認を組み合わせたAIを学ぶ。

## 2. 元ネタと教材化方針
- 元ネタ企業システム: Walmart / Starbucks Inventory AI
- 実企業システムそのものを再現するのではなく、企業AIシステムの業務適用パターンを学ぶ教材として小さく実装する。
- 商品・顧客・注文管理へ統合する最終ポートフォリオは対象外とする。
- `system17` から `system36` のAI基礎・評価教材とは分け、業務実行・推薦・予測・検知・最適化・KPI評価を扱う。

## 3. 対象ユーザー
- AIを業務システムへ組み込む設計を学習する開発者
- AIを文章生成部品ではなく、業務判断と業務実行へ接続する流れを学びたい学習者

## 4. 入力
販売履歴、在庫数、入荷予定、季節性、イベント、リードタイム、発注制約

## 5. 出力
需要予測、欠品リスク、推奨発注量、補充理由、承認待ち一覧

## 6. 機能要件
- 時系列データから需要を予測する
- 在庫日数と欠品リスクを計算する
- 発注点を超えた商品を抽出する
- 補充提案を理由付きで作る
- 人間承認後に発注候補として記録する

## 7. 非機能要件
- ローカルで再現できる小さなサンプルとして構成する。
- 外部AI APIが必要な箇所は、モックまたはサンプルデータで代替できる設計にする。
- LM Studio を使う場合、本体は Docker 化せず、既存 `system01` から `system16` と同じくローカル起動し、Docker からは `host.docker.internal` 経由で接続する。
- Docker に入れられる実装は、製造工程で既存 StudyAI の共通 Docker 構成に統合する。
- 作成・更新するテキストファイルは UTF-8 BOMなしを原則とする。
- 判断結果、実行結果、失敗理由、評価指標は直近20件をUTF-8のJSONへ保存し、StudyAI再起動後も確認できるようにする。

## 8. 受入条件
- LLMではなく予測と業務ルールの組み合わせとして説明できる
- 予測誤差と欠品リスクを分けて表示できる
- 自動発注ではなく承認フローを挟める
- StudyAI再起動後も、補充提案、承認結果、発注候補、監査記録を同じ実行番号で確認できる

## 9. 後続工程への引き継ぎ
- 基本設計では、入力、処理、出力、保存形式、UI、API、承認・監査・評価の境界を定義する。
- 詳細設計では、request / response schema、状態遷移、エラーコード、Docker 実行入口、検証コマンドを定義する。
- 製造では、StudyAI 型の共通アプリ構成に統合し、README、demo、test、検証記録、自己レビューを作成する。

## 10. 対象外
- 実企業サービスの完全再現
- 本番クラウド連携
- 課金が発生する外部APIを必須にした実装
- 商品・顧客・注文管理の統合ポートフォリオへの組み込み
