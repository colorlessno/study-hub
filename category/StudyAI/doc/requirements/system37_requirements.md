# System 37 要件定義

## このテーマでできるようになること

- 券売機型の単純選択とAIコンシェルジュ型の違いを説明できる
- 条件不足時に追加質問できる
- 実行前確認と実行後記録が分かれている

## 取引実行型AIコンシェルジュ

## 1. 目的
利用者が答えを知らない状態から条件を聞き出し、候補比較、確定処理、変更取消まで進める業務実行型AIを学ぶ。

## 2. 元ネタと教材化方針
- 元ネタ企業システム: IndiGo 6Eskai
- 実企業システムそのものを再現するのではなく、企業AIシステムの業務適用パターンを学ぶ教材として小さく実装する。
- 商品・顧客・注文管理へ統合する最終ポートフォリオは対象外とする。
- `system17` から `system36` のAI基礎・評価教材とは分け、業務実行・推薦・予測・検知・最適化・KPI評価を扱う。

## 3. 対象ユーザー
- AIを業務システムへ組み込む設計を学習する開発者
- AIを文章生成部品ではなく、業務判断と業務実行へ接続する流れを学びたい学習者

## 4. 入力
利用者の希望条件、候補マスタ、空き枠、価格、本人確認状態、変更取消条件

## 5. 出力
聞き出した条件、候補一覧、推奨理由、確定前確認、実行結果、取消可否

## 6. 機能要件
- 条件聞き出しを段階的に行う
- 候補を比較し理由付きで提示する
- 確定前に利用者確認を必須にする
- 予約・申込・注文を模した教材上の取引について、実行、変更、取消の結果を記録する
- 変更取消条件を判定する
- 判断結果、実行結果、失敗理由、監査記録、評価指標を同じ実行番号へ関連付ける
- 保存した実行履歴をアプリケーション再起動後も確認できる

## 7. 非機能要件
- ローカルで再現できる小さなサンプルとして構成する。
- 外部AI APIが必要な箇所は、モックまたはサンプルデータで代替できる設計にする。
- LM Studio を使う場合、本体は Docker 化せず、既存 `system01` から `system16` と同じくローカル起動し、Docker からは `host.docker.internal` 経由で接続する。
- Docker に入れられる実装は、製造工程で既存 StudyAI の共通 Docker 構成に統合する。
- 作成・更新するテキストファイルは UTF-8 BOMなしを原則とする。
- 判断結果、実行結果、失敗理由、監査記録、評価指標はUTF-8のJSONファイルへ永続化する。
- 実行履歴は直近20件を保存し、アプリケーション再起動後も同じ履歴を確認できるようにする。
- 永続化ファイルは一時ファイルへ書き込んでから置換し、書き込み途中の内容を履歴として扱わない。

## 8. 受入条件
- 券売機型の単純選択とAIコンシェルジュ型の違いを説明できる
- 条件不足時に追加質問できる
- 実行前確認と実行後記録が分かれている
- 実行、変更、取消、条件不足、確認待ち、条件不一致の結果が履歴へ保存される
- アプリケーションを再起動しても保存済み履歴を取得できる

## 9. 後続工程への引き継ぎ
- 基本設計では、入力、処理、出力、保存形式、UI、API、承認・監査・評価の境界を定義する。
- 詳細設計では、request / response schema、状態遷移、エラーコード、Docker 実行入口、検証コマンドを定義する。
- 製造では、StudyAI 型の共通アプリ構成に統合し、README、demo、test、検証記録、自己レビューを作成する。

## 10. 対象外
- 実企業サービスの完全再現
- 本番クラウド連携
- 課金が発生する外部APIを必須にした実装
- 商品・顧客・注文管理の統合ポートフォリオへの組み込み
