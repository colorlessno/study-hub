# 最終成果物 要件定義

## 何を作るか（システム概要）

**ギフのC向け AIアシスタント機能**
ユーザーが贈り物の相談をすると、会話で条件を引き出し、自社商品DBから適切な候補を推薦し、LLMが推薦理由を生成して返すシステム。

---

## 構成要素

### 1. 商品・オントロジーDB（PostgreSQL + pgvector）

> 📝 **オントロジーとは**
> 「商品」「贈答シーン」「贈答相手」「価格帯」といった概念と、その概念同士の関係を整理したデータ構造のこと。単なるマスタテーブルとの違いは、「焼き菓子 → 常温保存可 → 手土産向き」「高級酒 → 目上向け → 好み差が大きい」のように、**意味のつながりをデータとして持つ**点にある。これがあることで、AIが「義実家への初訪問なら派手すぎないものを出す」といった文脈判断をしやすくなる。

- 商品マスタ（商品名、カテゴリ、価格帯、在庫、フォーマル/カジュアル度など）
- 贈答シーン辞書（母の日、お中元、出産祝い、etc）
- 贈答相手分類（上司、友人、義実家、etc）
- NG条件マスタ（食品NG、酒NGなど）
- 商品↔シーン↔相手の意味関係テーブル

---

### 2. 検索・フィルタリング層

- キーワード検索
- 属性・価格帯・在庫フィルタ
- オントロジーによる不適切候補の除外

  > 📝 ここでのオントロジーの役割は「除外ルールの根拠データ」。例えば「出産祝いには縁起上避けるカテゴリがある」という意味関係がオントロジーに登録されていれば、プログラムがそのルールを参照して自動除外できる。

- スコアリング関数

---

### 3. コンシェルジュAPI（FastAPI）

- `POST /gift-concierge/chat` — 会話で条件収集、未入力項目を検出して質問返し
- `POST /gift-concierge/recommend` — 条件が揃ったら推薦候補を返す
- 会話状態の管理（セッション or DB保存）

---

### 4. 推薦・説明生成層

- ルール＋スコアリングで候補を上位3〜5件に絞る
- LLMで各候補の推薦理由・注意点・向く相手を生成
- 出力はJSON固定（`title`, `reason`, `price_band`, `warnings`）
- 壊れたJSON再試行処理込み

---

### 5. エージェントループ（LangGraph）

使用ツール一覧：

- `search_products`
- `check_inventory`
- `get_gift_rules`（オントロジー参照）

  > 📝 `get_gift_rules` がオントロジーを参照するツール。エージェントがこのツールを呼ぶことで、「このシーン・この相手に対してどんな商品が向くか／避けるべきか」という意味ルールを動的に取得できる。LLMが直接判断するのではなく、事前に設計した意味構造を根拠として使う点がポイント。

- `generate_reason`
- `ask_followup_question`

停止条件：

- 候補3件が出たら終了
- 追加質問は最大3回
- 在庫なし時は代替候補に切り替え

---

### 6. 評価・トレース基盤（MLflow）

- 固定質問50本の評価データセット
- 候補妥当性・説明の自然さの採点シート
- 旧版/新版比較ログ
- トレース可視化

---

## 入出力の具体例

**入力（ユーザー）:**
> 「50代男性の上司に5,000円以内で外さないギフトを探したい。食品OK」

**システムの動き:**
1. 会話で不足条件を確認（季節、無難さ/意外性の優先度など）
2. 商品DBから価格帯・在庫・カテゴリでフィルタ
3. オントロジーで「目上向け」「無難寄り」を適用、不適切商品を除外
4. スコアリングで上位3件に絞る
5. LLMが推薦理由を生成

**出力（JSON）:**
```json
[
  {
    "title": "老舗和菓子 詰め合わせ",
    "reason": "目上の方への贈答として定番。常温保存可能で相手を選ばない。",
    "price_band": "3,000〜5,000円",
    "warnings": "甘いものが苦手な場合は要確認"
  }
]
```

## 明示的に対象外にするもの

- 汎用の万能AIエージェントではない（EC推薦ドメイン特化）
- 決め打ちフローのバッチ処理部分はLLMに頼らない
- UI（フロントエンド画面）はスコープ外。APIまで作る
