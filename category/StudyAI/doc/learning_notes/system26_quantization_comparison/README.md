# system26 量子化方式の比較

同じ基本モデルを異なる量子化方式で実行し、メモリ使用量、応答時間、回答品質の違いを比較するテーマです。

## このテーマでできるようになること

- 量子化方式以外の条件を揃えて比較できる
- 各モデルの回答、メモリ使用量、応答時間、品質点を同じ表で確認できる
- メモリ、速度、品質、総合の優先条件によって採用候補が変わる理由を説明できる
- 実モデルの結果と明示的なモックを区別できる
- 比較結果と採用判断を保存し、後から確認できる

## 最初に取り組むこと

1. LM Studioへ比較する量子化モデルを読み込む。
2. `quantization_profiles`の`model`を、LM Studioに表示されるモデル名へ書き換える。
3. 同じ実行環境で確認した各モデルのメモリ使用量を、`runtime_metrics`の`memory_mb`へ入力する。
4. 全モデルへ共通で送る`prompt`、`temperature`、`evaluation_rubric`を確認する。
5. `mode`を`model`にして実行する。
6. 比較表を確認し、`learning_note`へ観察結果、採用判断、残る注意点を書く。

画面と比較手順だけを確認するときは、`mode`を`mock`にします。モックは実モデル通信に失敗したときの代替結果ではありません。

## 画面で確認すること

- 比較方法が「実モデルへの通信」または「明示的なモック」と表示される
- 指定したすべてのモデルに同じ指示とTemperatureが使われる
- 指定モデルと実際に応答したモデルが表示される
- 各方式の回答、メモリ使用量、応答時間、品質点、総合点が同じ表に表示される
- メモリ最小、最速、品質最高の方式が別々に表示される
- 優先条件を変えると、採用候補と選択理由が対応して変わる
- 実行結果がJSONへ保存され、履歴に残る

## 入力項目

### `quantization_profiles`

比較する方式ごとに、重複しない`id`と`model`、画面表示用の`label`、量子化方式を表す`quantization`を指定します。`mock_response`は明示的なモックだけで使います。

### `runtime_metrics`

各プロファイルの`profile_id`、実測した`memory_mb`、比較条件を記録する`environment_note`を指定します。`mock_elapsed_ms`は明示的なモックだけで使います。

### `evaluation_rubric`

回答に必要な`required_terms`、回答長の目安`max_length`、網羅率と簡潔さの重みを指定します。重みの合計は1にします。

### `selection_priority`

- `memory`: メモリ使用量が小さい方式を優先する
- `speed`: 応答時間が短い方式を優先する
- `quality`: 品質点が高い方式を優先する
- `balanced`: 品質50%、メモリ25%、速度25%の総合点で比較する

## 処理のつながり

画面から比較条件をAPIへ送ると、バックエンドは量子化プロファイルを入力順に一件ずつLM Studioへ送り、直前の応答完了後に次へ進みます。同時送信はしません。応答時間を計測し、入力されたメモリ使用量と固定した品質評価を組み合わせて比較表を作ります。結果は画面へ返し、`system26_runs.json`へ保存します。

## 数値の読み方

- 応答時間はStudyAIがモデル通信の開始から完了までを計測した値です。
- メモリ使用量はLM Studioなどで利用者が確認して入力した値です。
- 品質点は必須語句の網羅率と回答長で計算する教材用の値です。
- 量子化方式だけを比較するには、基本モデル、指示、Temperature、コンテキスト長、実行環境を揃えます。

## うまく動かないとき

- LM Studioが起動し、OpenAI互換APIのポートが`5858`になっているか確認する
- `quantization_profiles[].model`がLM Studioのモデル名と一致するか確認する
- 各`profile_id`に対応する`runtime_metrics`があるか確認する
- `memory_mb`が0より大きいか確認する
- 評価の重みが0以上で合計1になっているか確認する
- 実通信できない場合は自動的にモックへ切り替わらないため、通信エラーを解消する
