# system46 AI作業の実行基盤設計

AIへ渡す作業入力と、入力・操作・出力を検証する処理を組み合わせ、同じ条件で再確認できる構成を確認します。

## このテーマでできるようになること

- 作業入力に必要な項目を固定できる
- 入力不足と禁止操作を別の検証で判定できる
- AIの出力に必要な見出しを機械的に確認できる
- 正常例と異常例を保存し、同じ検証を繰り返せる
- プロンプトだけの場合と、入力・検証・権限・記録を組み合わせる場合の違いを説明できる
- 検証結果、失敗理由、再実行条件、改善メモを実行記録として保存できる

## 最初に取り組むこと

1. 「正常な入力構造を検証」と「入力不足を検出」を実行し、結果を比較する。
2. 「許可された操作を検証」と「禁止操作を検出」を実行し、操作の境界を確認する。
3. 「出力形式を検証」を実行し、期待する出力例の見出しを確認する。
4. 教材欄で入力例と各検証処理を開き、どの記述を判定しているか確認する。
5. 実行結果の `failure_reason`、`rerun_condition`、`feedback_memo`、`log_path` を確認する。

## 操作と確認結果

| 操作 | 確認する結果 |
| --- | --- |
| 正常な入力構造を検証 | 必要な4項目が揃っているため成功し、実行記録が保存される |
| 入力不足を検出 | 不足項目、失敗理由、再実行条件が記録される |
| 許可された操作を検証 | 禁止操作が含まれないため成功し、実行記録が保存される |
| 禁止操作を検出 | 検出した禁止操作と承認境界の見直し方が記録される |
| 出力形式を検証 | 指摘、要約、残リスクの見出しが揃っているため成功し、実行記録が保存される |

## 実行記録

各検証は、次の項目をJSONで画面へ返し、`samples/run_logs/`へ1実行1ファイルのUTF-8 JSONとして保存します。成功と失敗は別々のファイルに残るため、同じ入力で再実行した結果を後から比較できます。

| 項目 | 内容 |
| --- | --- |
| `run_id` | 実行を識別するID |
| `task_id` | 入力または出力ファイルから判別した作業ID |
| `fixture` | 検証した入力または出力ファイル |
| `started_at` / `ended_at` | 開始時刻と終了時刻 |
| `checks` | 実行した検証名、結果、メッセージ |
| `result` | 検証全体の `passed` または `failed` |
| `failure_reason` | 失敗した理由 |
| `rerun_condition` | 再実行前に直す内容 |
| `feedback_memo` | 次回の入力、検証、承認境界へ反映する内容 |
| `residual_risk` | 検証後も人間が確認する必要がある内容 |
| `log_path` | 保存した実行記録の場所 |

## 構成

- `fixtures/` に正常例と異常例を置く。
- `checks/` に入力、操作、出力の検証処理を置く。
- `samples/expected_output.md` に期待する出力形式を置く。
- `samples/run_logs/` に実行ごとのJSON記録を保存する。
- `docs/approval_boundary.md` に人間の承認が必要な操作を定義する。
- `docs/feedback_loop.md` に失敗結果を次の修正へつなぐ手順を記載する。

## 実行記録を確認する

1. 画面からいずれかの検証を実行する。
2. 結果の`log_path`を確認する。
3. `category/StudyAI/src/apps/system46_ai_harness_engineering/`からの相対パスとして、保存されたJSONを開く。
4. 同じ操作を再実行し、別の`run_id`とJSONファイルが作成されることを確認する。
5. 成功例と失敗例の`checks`、`failure_reason`、`rerun_condition`、`feedback_memo`を比較する。
