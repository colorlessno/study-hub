# system40 需要予測・在庫最適化AI

販売履歴と販促条件から需要を予測し、在庫制約を守る補充量と承認結果を保存するテーマです。

## このテーマでできるようになること

- 基礎予測と販促条件を反映した需要予測を比較できる
- 需要予測の誤差と在庫不足による欠品リスクを分けて確認できる
- 最低在庫と棚容量を守る補充量を確認できる
- 補充提案を承認待ちで保存し、人間の承認後だけ発注候補へ記録できる

## 最初に取り組むこと

1. StudyHubでsystem40を開く。
2. 既定値で実行し、基礎予測、販促倍率、需要予測、補充量を確認する。
3. promotion_calendarのliftを変更し、需要予測と補充量の変化を比較する。
4. inventory_snapshotの現在庫を変更し、欠品の注意点と補充量を確認する。
5. shelf_capacityを変更し、目標在庫が棚容量を超えないことを確認する。
6. approval.statusがpendingのまま実行し、自動発注されないことを確認する。
7. approval.statusをapprovedへ変更し、承認者と発注候補が実行履歴へ保存されることを確認する。
8. StudyAIを再起動し、同じ補充提案、承認結果、発注候補、監査記録が実行履歴へ復元されることを確認する。

## 画面で確認すること

- 直近三件の販売数から基礎予測を計算する
- 販促倍率を基礎予測へ反映する
- 季節倍率とリードタイム内の入荷予定を予測・在庫計算へ反映する
- 実績値がある場合は需要予測の誤差率を表示する
- リードタイム中の需要と現在庫から欠品リスクを判定する
- 最低在庫と棚容量の範囲で目標在庫と補充量を計算する
- 補充理由と承認状態を保存し、承認前は発注候補を記録しない
- 承認後だけ補充量を発注候補として実行履歴へ記録する

## 処理のつながり

画面の販売履歴、季節倍率、販促予定、在庫、入荷予定、リードタイム、店舗制約、承認状態をAPIへ送ります。APIは需要予測、誤差、欠品リスク、目標在庫、補充量を計算し、補充提案と承認結果を同じ実行履歴へまとめます。直近20件はUTF-8のJSONへ保存され、StudyAI再起動後に読み戻されます。

## この実験で確認できる範囲

移動平均、季節倍率、販促倍率を使った簡易予測です。統計モデルや機械学習モデルによる予測、外部発注システムへの送信、複数店舗間の在庫配分は行いません。承認済みの補充量は、StudyAIバックエンドのJSON実行履歴へ発注候補として記録します。

## うまく動かないとき

- sales_historyが数値の配列か確認する
- inventory_snapshotに在庫数が一件以上あるか確認する
- 既定値へ戻してから再実行する
