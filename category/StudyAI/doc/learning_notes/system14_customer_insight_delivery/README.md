# system14 顧客接点データ分析・インサイト配信

顧客対応データを取り込み、集計、分析、質問応答、配信設定までを確認するテーマです。

## このテーマでできるようになること

- 教材用データまたは手元のファイルを取り込める
- 取込状態とダッシュボードの集計結果を確認できる
- 条件を絞って顧客の声、営業スコア、受注・失注要因を比較できる
- 分析AIの回答と根拠を確認できる
- 分析結果の配信方法を設定し、実行結果を確認できる
- ローカル・ダミーCRMへ顧客対応履歴をHTTP送信し、保存結果と対応状態を確認できる
- 音声・動画ではfaster-whisperの区間時刻とローカルpyannoteの匿名話者ラベルが発話と一緒に保存されることを確認できる
- ルール分析とLM Studio・LangGraph分析を明示的に選択し、外部モデル利用の有無と失敗境界を比較できる
- FAQ、過去の発話、営業スコア、完了済みCRM対応をRAG検索し、参照根拠付きの回答を確認できる
- 緊急度が高い発話を取込時に検知し、リアルタイムworkflowの配信結果を履歴で確認できる

## 最初に取り組むこと

1. 「データ取込」で「教材用データを取り込む」を押す。
2. 「状態更新」を押し、取込状態が「完了」になったことを確認する。
3. 「ダッシュボード」で会話数、感情別の発言数、顧客の声ランキングを確認する。
4. 「分析」で商品、問い合わせ理由、感情、担当者、発言種別を指定し、結果の違いを確認する。
5. 「エージェント」で質問し、回答、推奨する行動、回答の根拠を確認する。
6. ワークフローの配信方法を「ローカル・ダミーCRMへ送信」にし、顧客ID、顧客名、担当者、緊急度を入力して「保存して実行する」を押す。
7. 「ダミーCRM」を開いて「登録内容を更新」を押し、送信した顧客対応履歴が表示されることを確認する。
8. 対応状態を「対応中」「完了」の順に更新し、画面を更新しても状態が保持されることを確認する。
9. 「RAG・FAQ」でFAQを保存し、「発話・スコア・完了済み対応の索引を更新」を押す。
10. 「エージェント」でRAG検索を有効にして質問し、FAQ・発話・完了済みCRM対応の類似度付き根拠を確認する。
11. 必要に応じて、ダッシュボード保存、WebhookのHTTP送信、SMTPメール送信も確認する。実CRMは接続環境が提供されていないため送信対象にしない。

リスク即時通知を確認する場合は、データ取込画面の取得元を`studyhub_sample`にしてから、エージェント画面で実行タイミングを「リアルタイム」、配信方法を「ダッシュボードに保存」としてworkflowを登録します。その後に教材用データを取り込むと、「至急」を含む発話が緊急度`high`として検知されます。「リスク即時アラート履歴」の「履歴を更新」を押し、発話、件数、配信方法、成功・失敗がDBから読み戻されることを確認します。

手元のデータを使う場合は、取込種別、取得元、共通情報を指定してファイルを取り込みます。JSONファイルは配列、または `items` 配列を持つオブジェクトを使用します。

音声・動画を取り込む前に、`scripts/download-system14-diarization-model.cmd`で公式モデルを専用Docker volumeへ取得します。Hugging Face tokenは取得用コンテナだけへ渡され、通常のsystem14サービスでは使いません。取込時はfaster-whisperの文字起こし完了後にローカルpyannoteを順番に実行し、「保存した発話と時刻情報」へ匿名話者ラベル、開始秒、終了秒を表示します。話者区間と重ならない発話は「未識別」と表示し、匿名ラベルを顧客・担当者へ推測で変換しません。モデル未配置や読込み失敗時は取込を失敗として表示し、全区間を未識別にする自動切替は行いません。

「発話分析方法」で「ルール分析」を選ぶとローカルの決定規則だけを使います。「LM Studio・LangGraph分析」を選ぶと、個人情報をマスクした発話を一件ずつ順番にLM Studioへ送り、JSON応答をLangGraphで検証して保存します。接続失敗や不正な応答をルール分析へ自動切替しないため、失敗時はジョブ状態とエラーを確認してください。

## 画面で確認すること

- 取込処理で入力の正規化と個人情報のマスクが行われる
- 音声・動画の文字起こし区間ごとに匿名話者ラベル、開始秒、終了秒がDBへ保存され、取込画面で確認できる
- LM Studio・LangGraph分析では、マスク済み発話が一件ずつ順番に処理され、不正応答が成功扱いにならない
- 取込結果がダッシュボードと分析結果に反映される
- 顧客の声と営業担当者の発言から異なる分析結果が作られる
- 分析AIの回答に集計結果が根拠として表示される
- 「ダッシュボードに保存」では、配信内容と実行結果がバックエンドAPI経由でDBに保存される
- WebhookではHTTP POST、メールではSMTPを使い、送信結果もDBに保存される
- ダミーCRMではBearer認証付きHTTP POSTを実行し、顧客対応履歴と元の分析ペイロードがDBに保存される
- 同じworkflowの送信をやり直しても、外部IDによって重複行が作られない
- ダミーCRMの対応状態を未対応、対応中、完了へ更新できる
- 実CRMは接続環境が提供されていないことが明示され、送信しない
- FAQが本文、商品、EmbeddingとともにPostgreSQLへ保存される
- 発話、営業スコア、完了済みCRM対応が一件ずつ順番に索引化され、RAG回答に参照元と類似度が表示される
- LM Studio接続失敗時にキーワード検索や画面内回答へ自動切替しない
- 取込元が一致するリアルタイムworkflowは、緊急度`high`の発話を保存した直後にID順で一件ずつ配信し、結果をDBへ保存する
- リスク即時アラート履歴で、検知した発話、件数、取込元、配信方法、成功・失敗、エラーを確認できる

## 処理のつながり

取込処理が入力を正規化し、個人情報をマスクして保存します。発話分析、集計、営業評価が同じデータを利用し、質問応答と配信処理が分析結果を利用します。緊急度`high`の発話は保存直後に取込元が一致するリアルタイムworkflowへ渡し、各配信をID順に完了して結果をDBへ保存します。ダミーCRM配信では分析結果を顧客対応履歴へ変換し、同じバックエンド内のAPIへ実際にHTTP送信してPostgreSQLへ永続化します。RAG索引更新は保存済み発話、営業スコア、完了済みCRM対応を順番にLM StudioでEmbedding化し、FAQと同じpgvector索引へ保存します。

## うまく動かないとき

- 「教材用データを取り込む」で動作を確認してから、手元のファイルを試す。
- 入力形式と取込種別が一致しているか確認する。
- 必須の取得元が入力されているか確認する。
- 「状態更新」を押し、取込処理が完了しているか確認する。
- 分析結果が空の場合は、絞り込み条件を解除する。
- ダミーCRM送信が失敗する場合は、`SYSTEM14_DUMMY_CRM_ENDPOINT`と`SYSTEM14_DUMMY_CRM_TOKEN`が設定され、system14が8014番で起動していることを確認する。
- RAG索引更新や回答が失敗する場合は、LM StudioでEmbeddingモデルと会話モデルがロードされ、StudyAIの設定先から到達できることを確認する。モデル識別子は環境設定を使用し、画面から固定しない。
- 音声・動画取込が話者分離モデル未配置で失敗する場合は、公式モデルの利用条件とread tokenを確認し、`scripts/download-system14-diarization-model.cmd`を一度実行する。通常のsystem14サービスへtokenを設定しない。
