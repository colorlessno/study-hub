# web35 HTTPステータス設計 要件定義

## 1. 目的

業務APIで使う HTTP status code を、正常、入力エラー、未認証、権限不足、未存在、競合、サーバーエラーに分けて理解する。

## 2. 学習対象

- 200 / 201
- 400
- 401 / 403
- 404
- 409
- 500
- error response body

## 3. 作成する成果物

- status code確認用API
- 正常系・異常系レスポンス例
- エラーレスポンス設計メモ
- curl確認手順

## 4. 機能要件

| ID | 要件 |
|---|---|
| FR-01 | 200 と 201 を使い分けられる |
| FR-02 | validation error として 400 を返せる |
| FR-03 | 401 と 403 を区別できる |
| FR-04 | resource not found として 404 を返せる |
| FR-05 | 二重登録や競合として 409 を返せる |
| FR-06 | 500 の扱いと内部情報を出さない方針を確認できる |

## 5. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | API利用者が原因を判断できるレスポンスにする |
| NFR-02 | 内部スタックトレースをレスポンスに出さない |
| NFR-03 | フロントエンドで扱いやすい形式にする |

## 6. 対象外

- OpenAPI生成
- 多言語エラーメッセージ
- 監査ログ

## 7. 受入条件

- 主要status codeを使い分けられる
- error response body の共通項目を説明できる
- API失敗時の原因候補を切り分けられる

## 8. 学習観点

- status code は画面表示ではなくAPI契約の一部
- 401と403を混同しない
- 500で内部情報を出さない
