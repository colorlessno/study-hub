# 表示方式比較表

## 基本となる方式

| 方式 | 主な動き | 強み | 注意点 | 向く例 |
|---|---|---|---|---|
| MPA | 画面遷移ごとにサーバーからページ全体を取得する | 処理の流れを単純にしやすい | 画面全体の読み直しが増える | 単純な登録・一覧画面 |
| SPA | 最初の画面を読み込んだ後、ブラウザがAPIと画面状態を管理する | 画面内の操作を連続して行いやすい | 読み込み中、認証切れ、エラーの状態管理が増える | 管理画面、編集画面 |
| SSR | 要求を受けた時にサーバーでHTMLを作る | その時点のデータを最初のHTMLへ含められる | サーバー負荷とキャッシュ範囲の判断が必要 | 更新のある公開ページ、認証済みページ |
| SSG | 配信前にHTMLを作る | 公開内容を安定して配信しやすい | 更新反映と再生成の方法を決める必要がある | ドキュメント、製品紹介 |

MPAとSPAは主に画面遷移とブラウザ側の状態管理を、SSRとSSGは主にHTMLを作る時点を表します。そのため、SSRで最初のHTMLを作り、以後はSPAのように画面を操作する構成もあります。

## 組み合わせる仕組み

| 仕組み | 主な動き | 強み | 注意点 |
|---|---|---|---|
| Server Components | 一部の画面部品とデータ取得をサーバー側で処理する | ブラウザへ送るJavaScriptを減らせる | サーバーとブラウザの境界を明確にする必要がある |
| Islands | 静的なHTMLを基本に、必要な部分だけをブラウザで動かす | 内容中心の画面でJavaScriptを減らせる | 動く部分をまたぐ状態共有が複雑になり得る |
| PWA | オフライン、インストール、通知等の機能を加える | 通信が不安定な場面にも対応できる | 古いキャッシュ、再送、権限、端末差を扱う必要がある |

## 判断の順序

1. 公開情報と非公開情報を分ける
2. 更新頻度と必要な画面操作を確認する
3. HTMLを作る場所と時点を決める
4. サーバーとブラウザの役割を決める
5. キャッシュする範囲と更新方法を決める
6. 実装、配信、監視、障害調査の複雑さを比較する
