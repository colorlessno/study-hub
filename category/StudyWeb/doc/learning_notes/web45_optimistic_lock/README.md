# web45 同時更新を防ぐ楽観ロック

利用者AとBが同じ版のデータを読み込み、先に保存された変更を古い版の保存で上書きしない仕組みを確認するテーマです。

## このテーマでできるようになること

- 2人が同じ版を読み込んだ状態を再現できる
- 読込時の版と現在の版を比較して更新競合を検出できる
- 競合した保存では、現在のデータを変更しないことを確認できる
- 最新版を読み直し、更新内容を再編集した後なら保存できることを確認できる

## 最初に取り組むこと

1. 「利用者Aが読込」「利用者Bが読込」を順番に押し、両者がAPIから版1と現在のnameを取得したことを確認する。
2. AとBの更新内容へ異なる値を入力する。
3. 「利用者Aが保存」を押し、APIがHTTP 200を返してAのnameが反映され、現在のレコードが版2になることを確認する。
4. 「利用者Bが保存」を押し、APIがHTTP 409を返して現在の版2と読込時の版1を示すことを確認する。
5. 競合後も、現在のレコードが利用者Aの内容のままであることを確認する。
6. 利用者Bがもう一度読み込み、最新版を確認して更新内容を再編集してから保存し、版3になることを確認する。
7. 「更新競合が発生する流れ」と実ソースを開き、画面の状態変化と照合する。

## 版の変化

| 操作 | 現在の版 | 利用者Aの読込時の版 | 利用者Bの読込時の版 |
|---|---:|---:|---:|
| 初期状態 | 1 | 未読込 | 未読込 |
| AとBが読込 | 1 | 1 | 1 |
| Aが保存 | 2 | 1 | 1 |
| Bが保存 | 2 | 1 | 1 |
| Bが再読込して保存 | 3 | 1 | 2 |

競合後に自動で再送すると、先に保存された変更を上書きする可能性があります。利用者へ最新データを示し、再確認と再編集を促す必要があります。

## この教材で扱わないこと

- DBの条件付きUPDATEと永続化
- 競合前後の内容を自動比較・統合する機能
- 悲観ロック

## 手動で確認する場合

APIと画面を起動します。

```bat
cd /d category\StudyWeb\src\frontend\static\studyweb\systems\web45_optimistic_lock\app
set PORT=43345
rtk node server.js
```

構文確認は次のコマンドです。

```bat
rtk node --check category\StudyWeb\src\frontend\static\studyweb\systems\web45_optimistic_lock\app\src\main.js
rtk node --check category\StudyWeb\src\frontend\static\studyweb\systems\web45_optimistic_lock\app\server.js
```

## うまく動かないとき

- 保存前に読込操作を行ったか確認する。
- 操作順が分からなくなった場合は、「初期状態に戻す」を押す。
- 競合の条件は、画面に表示される現在の版と読込時の版を比較する。
