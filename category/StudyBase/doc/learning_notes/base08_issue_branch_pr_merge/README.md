# base08 Issue・ブランチ・Pull Request・マージ・同期

Issueの目的からブランチ、差分、検証、レビュー対応、マージ、ローカルmainの同期までを一続きで確認します。Giteaを社内Gitサーバーに見立てた実操作と、外部通信を行わない一時Git環境での確認を選べます。実GitHubは変更しません。

## このテーマでできるようになること

- Issueから同期までの各段階で、目的、差分、検証、判断者を説明できる
- サーバー側でマージしたmainを、ローカルmainへ安全に同期できる

## 到達目標

- Issueの完了条件をPRの変更と検証へ対応付けられる。
- PRへ「何を変えたか」「なぜ」「どう確認したか」を書ける。
- レビュー指摘へ原因、対処、横展開、再確認で回答できる。
- mainへの直接pushを避け、レビュー担当の承認後にマージできる。
- サーバー側でマージされたmainをローカルへ安全に同期できる。

## 最初に取り組むこと

StudyHubの「Issueからマージ後の同期までを確認」を実行します。処理は一時フォルダだけを使い、次の順序とGitの状態を実行ログへ表示します。

```text
Issue → 作業ブランチ → 変更と検証 → push → Pull Request
      → レビュー対応 → マージ → ローカルmainの同期
```

Issue記入例の完了条件とPull Request記入例の変更・確認結果を対応させます。レビュー対応記入例では、修正内容だけでなく原因と再確認結果も確認します。

変更前の検証失敗も学習用に表示しますが、ホスト固有の一時フォルダ絶対パスは`<temporary-workspace>`へ置き換えて表示します。

StudyHubを使わず教材ファイルだけを検証するときは、リポジトリルートで次を実行します。

```bat
rtk node category\StudyBase\scripts\validate-studybase.mjs base08
```

## 実務に近い演習へ進む

StudyHubで「起動」を押した後、「別画面で開く」からGiteaを`http://127.0.0.1:3418/`で開けます。Giteaは埋め込み表示を許可しないため、StudyHub内のフレームではなく別画面を使用します。Issue、Pull Request、レビュー、マージを画面で操作する手順は「Gitea実操作手順」で確認します。

```text
Issue → ローカルの作業ブランチ → コミットと検証 → push
      → Pull Request → レビュー修正 → 承認 → サーバー側のmainへマージ
      → ローカルmainをpullで同期
```

「Giteaの状態を確認」ではコンテナの状態を、「Giteaのログを確認」では直近のログを確認できます。「停止」はコンテナを停止しますが、演習データを保存するnamed volumeは削除しません。

企業ごとにGitHub Flow、Git Flow、trunk-based developmentなど採用ルールは異なります。この演習では、小さな変更を短命ブランチとPull Requestでmainへ統合する一般的な基本形を扱います。

## 確認すること

- Issue、作業ブランチ、Pull Requestの目的が対応している。
- Pull Requestに変更内容と検証結果が記録されている。
- レビュー指摘への修正が同じ作業ブランチへ追加されている。
- サーバー側のmainとローカルmainが同じコミットを指している。
- 実GitHub、教材原本、現在のリポジトリが変更されていない。
