# arch02 証拠に基づく設計レビュー

## このテーマでできるようになること

- 設計上の指摘を、利用者や運用への影響から説明できる
- 指摘と、その根拠になるソースや実行結果を対応づけられる
- 確認済みの事実と未確認の推測を分けられる
- 未実施の確認内容と残るリスクを記録できる

## 目的

arch02専用のレビュー対象を実際に動かし、設計上の指摘を画面・API・SQLite・ログ・ヘルス確認の証拠に対応づけて説明する力を身につける。

## 最初に取り組むこと

arch02専用のタスク登録システムを起動し、期待仕様と実際の状態コードの差を確認します。

| 入力 | 値 |
|---|---|
| レビュー対象 | arch02内の画面、タスク登録API、SQLite、実行ログ、`/health`、`/ready` |
| 期待する設計 | `POST /api/tasks`がSQLiteへ保存し、HTTP 201を返す |
| 実際の確認対象 | 教材用の差異としてHTTP 202を返す実装 |
| 確認するファイル | `docs/review_target_design.md`、`app/server.js`、`e2e/review.spec.js` |

1. StudyHubからarch02を起動し、レビュー対象と期待仕様を確認する。
2. タスク登録APIを実行し、HTTP 202の応答とSQLiteの保存結果を確認する。
3. 画面または「curlによるAPI証拠」を使い、health、ready、実行ログとTrace IDを取得する。
4. 期待201と実際202の不一致について、影響・証拠・修正案を整理する。
5. 未対応、対応済み、リスク受容から対応状態を選び、残リスクとともにSQLiteへ保存する。

## 資料の使い方

1. 「レビュー対象の整理」で、対象と今回扱わない範囲を決める。
2. 「curlによるAPI証拠」で、HTTP要求とTrace IDを一つずつ確認する。
3. 「証拠の確認表」で、確認したファイルや実行結果を記録する。
4. 「主張と証拠の対応」で、設計上の主張と根拠を対応づける。
5. 「指摘の書き方」で、問題が与える影響から指摘を書く。
6. 「残るリスクの整理」で、未確認の内容と残る不確実性を記録する。
7. 「レビュー結果のひな形」で、短いレビュー結果をまとめる。
8. 保存したレビュー結果と実行証拠を照合し、根拠が不足している箇所を見つける。

## 自分の言葉で説明する

- 「テストがない」と「実装が誤っている」では、指摘の根拠がどう違うか。
- ファイルを読むだけで確認できることと、実際に動かさないと確認できないことは何か。
- 指摘の重大度を、利用者や運用への影響からどう説明するか。
- 修正案を採用しても残るリスクを、レビュー結果へどう残すか。
