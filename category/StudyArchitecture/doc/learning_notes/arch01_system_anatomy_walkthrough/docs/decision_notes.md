# arch01の構成判断メモ

| 判断 | 直接確認できる証拠 | この教材での利点 | 不利な点・代替案 |
|---|---|---|---|
| 画面とAPIを1つのNode.jsプロセスで提供する | `app/server.js`の静的配信とAPI route | 起動対象とログの境界が一つで追跡しやすい | 規模拡大時は画面とAPIを分離できる |
| arch01専用SQLiteへ注文とログを保存する | `orders`、`request_logs`のSQL | 停止・再起動後も証拠を読み出せる | 複数ホスト共有が必要なら外部DBを検討する |
| 各API要求にTrace IDを付ける | 応答と`request_logs.trace_id` | 画面操作、API応答、保存ログを対応付けられる | 分散システム化する場合は共通trace基盤が必要になる |
| healthとreadyを分ける | `/health`、`/ready`、障害モード | 生存と受付可否の違いを再現できる | 障害モードは教材用で本番障害注入ではない |
| ループバックだけで待ち受ける | `server.listen(..., '127.0.0.1')` | 学習用システムをローカルへ限定できる | 他端末から利用する要件には対応しない |

## 記録ルール

「なぜこの判断を採用したか」はソースだけでは断定できない場合がある。その場合、上表の利点は設計上の推測として扱い、直接確認できる事実と分けて記録する。
