# arch01 システム構成の読み解き

## このテーマでできるようになること

- ソースや設定ファイルを根拠に、システムの構成要素を説明できる
- 1つの処理について、入力から応答までの流れを追跡できる
- 確認済みの事実と推測を分けて記録できる
- 採用した構成の理由、不利な点、代替案を整理できる

## 目的

arch01専用の小さなシステムを動かし、実際のソース、HTTP通信、SQLiteの状態、実行ログから全体の構成と処理の流れを説明する力を身につける。

## 最初に取り組むこと

arch01専用システムを起動し、画面から注文を保存します。

| 入力 | 値 |
|---|---|
| 対象 | `category/StudyArchitecture/src/apps/arch01_system_anatomy_walkthrough` |
| 外部から見える動作 | 画面から注文を登録し、SQLiteへ保存して一覧とログに表示する |
| 最初に読むファイル | `app/public/index.html`、`app/public/main.js`、`app/server.js` |
| 今回追う流れ | 画面入力 → HTTP API → 入力検証 → SQLite保存 → ログ記録 → JSON応答 |

1. StudyHubからarch01を起動し、処理の流れを確認する。
2. 注文を保存し、SQLiteの一覧と同じTrace IDを持つ実行ログを確認する。
3. 障害モードを開始し、`/ready`と注文登録が失敗することを確認する。
4. 復旧後に`/ready`と注文登録が正常へ戻ることを確認する。
5. ソースと実行結果から確認した事実を、設計意図に関する推測と分ける。

## 資料の使い方

1. 「対象システムの整理」で、対象・利用者・外部から見える動作を決める。
2. 「構成要素の整理」で、システムを3段階に分ける。
3. 「処理とデータの流れ」で、1つのリクエストまたは処理を追跡する。
4. 「失敗時の動き」で、症状・疑う場所・確認する証拠を対応づける。
5. 「事実と推測の整理」で、断定できる内容と推測を分ける。
6. 「構成判断メモ」で、構成を採用した理由と代替案をまとめる。
7. 実際の画面・API・SQLite・ログと比較し、抜けている説明を見つける。

## 根拠として確認するもの

- ソースファイルと設定ファイル
- Node.jsサーバーの入口と環境変数
- APIのURLと処理
- SQLiteの表と保存結果
- 実行ログとヘルスチェック
- ブラウザまたはHTTPリクエストで確認した結果

## 自分の言葉で説明する

- システム外部・実行単位・内部部品を分けると、何が分かりやすくなるか。
- 画面からの注文登録と`/ready`の確認は、通る経路と目的がどう違うか。
- `/ready`が503で`/health`が200になる障害モードには、どのような意味があるか。
- ソースから確認できない設計意図を、事実と混同せずどう記録するか。
